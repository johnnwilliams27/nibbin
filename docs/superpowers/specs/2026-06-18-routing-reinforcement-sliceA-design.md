# Routing Reinforcement — Slice A (signal substrate + scoreboard) — Design Spec

**Date:** 2026-06-18
**Status:** Approved-path (user approved the architecture + all-three-signals scope 2026-06-18). First of two slices for the §4B/§7 "thin owned reinforcement over the bought gateway." Builds on the shipped router (`packages/router`, M6.5) + the synthesis arc (Composer #139/#141/#142, Planner #150, Crystallization #153). Design context: `2026-06-17-agent-synthesis-design.md` §4B (eval→routing loop, weight-class budgets), §7 (thin reinforcement layer).
**Goal:** Make per-function model performance **visible and queryable** — the foundation any reinforcement policy needs, immediately useful for the team's **manual, eval-gated** model choices, and the data that reveals whether the signal is strong enough to auto-act on (Slice B). **`route()` is unchanged — this is pure observability, zero routing-behavior change.**

## 1. Why signal-first (the honest scope)
Routing today is static: each task tier resolves to exactly ONE model (T1→Haiku, T2→Sonnet, + two Opus pins); `route()` returns a single hardcoded model id. There is **no candidate set to shift traffic among**, and a locked decision (M6.5 §9) requires **model swaps gated by the eval regression suite**. So an auto-reweighting loop has almost nothing to act on yet and would risk conflicting with the eval gate. Slice A therefore builds the **observability substrate** (the foundation a Slice-B policy needs anyway) and an internal **scoreboard** that immediately informs the manual, eval-gated swaps the team makes today — and surfaces provider model churn (a model silently degrading). No routing behavior changes.

## 2. Capture the missing signals (additive; populated at the existing seam)
`model_calls` (migration `20260612120000_m65_budget_cogs.sql`) already records `account_id, user_id, run_id, tier, task, model, tokens, cost_microusd, origin, channel, created_at`. The quality signal (`approvals.decision`/`edit_distance`, keyed by `run_id`) and cost are already recoverable. Add the three missing signals — all additive columns on `model_calls`, populated by `recordModelCall` (`apps/web/lib/llm/client.ts`):
- **`outcome text` (`'ok' | 'refusal' | 'error'`, default `'ok'`):** `recordModelCall` gains an `outcome` field. The `anthropicGenerate` paths that today fail *silently* (return null on a provider error / refusal / rate-limit) instead record a `model_calls` row with `outcome='error'` (or `'refusal'` when the model declines / a moderation stop) — so a failing model is no longer invisible. (Today a graceful failure leaves NO row; we add a row so the failure is ledgered.)
- **`degraded boolean` (default false):** `route()` already computes `degraded` (budget forced T2→T1). Thread `decision.degraded` into every `recordModelCall` call site so "how often did budget pressure downgrade this task" is queryable.
- **`latency_ms integer` (nullable):** time the model call (start→return) at the `anthropicGenerate` boundary and pass it to `recordModelCall`. Null when not measured (e.g. the no-key/fallback path).

`recordModelCall`'s signature gains `{ outcome?, degraded?, latencyMs? }` (all optional, back-compat — existing callers default `outcome='ok'`, `degraded=false`, `latency_ms=null`). The ~7 call sites (`drafting.ts`, `synthesis.ts`, `understanding.ts`, `label.ts`, `extract.ts`, the composer/planner/crystallize soft-layer calls, the keeper chat) pass `decision.degraded` + the measured latency + the outcome.

## 3. The aggregated performance view
A **plain SQL view** (not materialized — internal read volume is low, always-fresh is simplest; materialize later only if needed) + a read RPC, in migration `20260618170000`:
`model_task_performance`: for each `(model, task)` over a rolling 30-day window —
`calls`, `approved_unedited_rate` (`approvals.decision='approved' AND edit_distance=0` / decided runs), `edited_rate`, `rejected_rate`, `avg_edit_distance`, `refusal_rate` + `error_rate` (from `outcome`), `degradation_rate` (`degraded`), `avg_cost_microusd` + `total_cost_microusd`, `avg_latency_ms`, `last_call_at`.
- Join `model_calls` LEFT JOIN `approvals` ON `run_id` (not every call has a run_id — diagnosis/chat calls have no approval; their quality rows are simply null on the approval columns, counted only in volume/cost/outcome). Quality metrics are over the subset with a `run_id` + an approval.
- **Privacy:** aggregate counts only — derived-not-raw, NO message content, NO per-user content. A staff read surface; cross-account aggregation is acceptable for an internal scoreboard (it's model-performance telemetry, not user data). The RPC is staff-gated (service-role / `staff_users`), never exposed to account users.

## 4. The scoreboard (read surface)
A **staff-gated scoreboard** (reuse the `staff_users` permission gate) in the admin app: the `model_task_performance` table, grouped by task with per-model rows, sortable by approved-unedited rate / refusal rate / cost / volume. So when the team weighs an eval-gated model swap or watches for churn, they see e.g. "`specialist_draft`: Haiku — 58% approved-unedited, 6% refusal, $X/call, 1.2k calls/30d." Read-only; no actions (Slice A changes nothing about routing). If the admin app has an existing analytics area, slot it there; else a new `/admin/...` route behind the staff gate.

## 5. Boundaries
- **In (A):** the three additive `model_calls` signals + `recordModelCall` plumbing + the call-site wiring; the `model_task_performance` view + staff read RPC; the staff scoreboard. Migration to dev/staging/prod.
- **Out (Slice B):** ANY change to `route()` / `tiers.ts` / candidate sets / auto-reweighting / fallback chains. Slice A does not alter which model is chosen for any task. (Slice B: candidate sets = the eval-cleared allowlist; a deterministic weighting that shifts traffic among pre-vetted models by quality-within-budget, with min-volume floors.) Also out: materialized rollup (until volume warrants); latency at sub-call granularity (one number per call).

## 6. Gating + tests
- **Gated** (`model_calls` migration + `recordModelCall` + the view/RPC + a staff surface) → `docs/gates/` report + 4-reviewer adversarial gate + dev/staging/prod apply.
- **Security/privacy testing:** the scoreboard is aggregate-only (no message content, no per-user content) + staff-gated (a non-staff account user cannot reach the RPC/page); the new columns are additive + back-compat (existing `recordModelCall` callers unaffected; the no-key path records `outcome='ok'`/null latency cleanly); recording a failure row must NOT leak prompt/response content (only model/task/outcome/tokens=0). **No routing behavior change** — a test asserts `route()` returns the same model for the same input as before (pure observability).
- **Tests:** `recordModelCall` writes `outcome`/`degraded`/`latency_ms` correctly (incl. an error-path row with `outcome='error'`, tokens 0, no content); the view computes approved-unedited/refusal/degradation/cost correctly over a seeded fixture (incl. calls with no `run_id` counted in volume but not quality); the staff RPC rejects a non-staff caller; the no-key path records cleanly; verification (tsc + vitest + eslint + next build for both apps/web and apps/admin if touched).
